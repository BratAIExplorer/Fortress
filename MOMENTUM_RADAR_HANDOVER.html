1. What Momentum Radar is, in one paragraph

A momentum scanner that watches all 500 Nifty stocks and flags the moment a stock's momentum flips from falling to rising (a MACD crossover). It runs on two timeframes — Daily and Weekly — and for each flagged stock it shows the current price, two upside targets, and a stop loss.

Momentum Radar is the timing layer. It is the only tab that is time-sensitive, which is exactly why it is the natural home for push alerts (Telegram) rather than pull (web).

2. How the flow works today

MACD BOT (/opt/macd-bot on VPS 76.13.179.32, PM2 managed) scans Nifty 500 every 5 minutes │ ├──► ZERODHA ─────► places REAL orders [OWNER'S account only. Private. Never exposed to users.] │ ├──► TELEGRAM ────► sends alert [OWNER'S chat only. One person. Not a user feature yet.] │ └──► HTTP POST ───► /api/analysis/momentum-signals (auth: shared secret x-cron-secret) │ macd_signals table ⚠ SNAPSHOT, NOT HISTORY │ GET /api/analysis/momentum-signals (currently ungated) │ /momentum-radar tab ── visible to everyone, read-only

Key design decisions already locked in

  • Trading stays private. Order execution runs on the owner's personal Zerodha keys inside the standalone bot. The website mirrors signals only — no Buy/Sell buttons, no per-user broker credentials. This deliberately avoids broker-credential custody and the compliance scope that comes with it.
  • Fail-safe ingest. The bot's push to Fortress is wrapped in try/except. If the website is down, the bot keeps trading. A marketing feature must never be able to break the trading loop.
  • Reused auth pattern. Ingest uses the same x-cron-secret shared-secret pattern as the existing scanner cron. No new dependency added to the bot.

4. Agreed beta plan

Owner decision — 29 July 2026
  • Beta is free and open to all, no login, for 1–2 weeks.
  • Purpose of beta: prove the signals are correct and useful before charging for them.
  • After beta: enable the authentication gate. Only authorised users see alerts, on web and Telegram.
  • Free trial model going forward: 30 days, all features unlocked — not a crippled tier.
  • Buy/Sell action layer is reserved for a Top / exclusive tier only.

Tiering must be account-level, not feature-level

5. Pre-production backlog — must be closed before commercialising

P0 — Blocker
1. Signal history & accuracy tracking — the table currently deletes itself

The problem, plainly: every 5 minutes the bot sends its current list and the API wipes the table and rewrites it:

await tx.delete(macdSignals);      // erases everything
await tx.insert(macdSignals)...    // writes the fresh snapshot

macd_signals is a whiteboard, not a ledger. A signal fires on a stock Monday, reaches its target Wednesday, drops off the bot's active list — and every trace of it is deleted. Permanently.

Consequence: we cannot answer "what is your hit rate?" — the single most important question any paying user will ask. It also cannot appear in the UI or in the bot health check. And this is off-brand: Fortress's stated principle is transparency, explainable scores, no black box, and Hidden Gem Finder already tracks outcomes properly via the trades table with win-rate by score band.

Fix: add an append-only macd_signal_history table. On each ingest, diff the new snapshot against the previous one — symbols that appear get an OPEN row; symbols that vanish get closed with an outcome (TARGET_HIT / STOPPED_OUT / EXPIRED) derived from last known price versus target and stop loss. Surface as a "Track Record" panel on the tab, and as a freshness/accuracy line in the admin health check.

Effort: ~1 day  ·  Why it cannot wait: every day without it is a day of accuracy data that can never be recovered. If we start logging only at launch, the honest answer on day one of charging money is "I don't know yet."
P0 — Privacy leak
2. The owner's position sizing is on a public page

The macd_signals table carries quantity, invested_amount and risk_amount — these come from the owner's own Zerodha position sizing, and the GET endpoint is currently ungated. Anyone visiting the page can see how much money the owner puts into each trade.

Fix: strip those three fields from the public GET response. Effort: ~5 minutes.
P0 — Compliance
3. Signal language — observation vs. recommendation

There is a meaningful difference between these two sentences:

  • "MACD crossover detected on SBIN. Price crossed above its signal line." — an observation. Describes what the market did.
  • "Buy SBIN. Target ₹X. Stop loss ₹Y." — a recommendation. Tells a person what to do with their money.

A read-only public web table sits closer to the first. A paid push notification to a stranger's phone, telling them to buy at a price with a stop loss, sits much closer to the second — which is SEBI Research Analyst / Investment Adviser territory in India. It is the paywall plus the push that changes the risk profile, not the wording alone.

Owner decision (29 Jul): continue beta as-is with current wording. This is logged as P0 and must be resolved before the first rupee is charged. Needs proper Indian regulatory review, not a judgement call.

P0 — Do within 1 week
4. Separate the trading bot from the user-alerts bot
Explained simply

Think of a Telegram bot as a phone number.

Right now there is one phone number. The trading bot uses it to text the owner: "I just bought 50 SBIN."

If that same number is later given to 500 customers:

  • Everyone's messages arrive through the same phone. Wires get crossed.
  • Telegram limits how many messages one number can send per second. A blast to 500 customers could delay the owner's own trade alert — the one message that actually needs to arrive instantly.
  • If a customer reports or blocks the number and Telegram restricts it, the owner's trading alerts die too.
  • Customer messaging can never be changed without touching the live trading setup.

So: get a second phone number. One bot for the owner's trading, one separate "Fortress Alerts" bot for customers. Creating a new Telegram bot is free and takes two minutes today. Untangling them after 500 people are on it takes a weekend.

Owner decision: approved, to be done within one week, before any user-facing Telegram work begins.
P1 — Beta quality
5. UI cannot distinguish "no signals" from "bot is dead"

The tab currently shows "no active crossovers" — which reads identically whether the market genuinely has no crossovers or the bot crashed on Tuesday. This is the exact state the product is in right now, and it is invisible from the page.

Fix: show a "Last updated: HH:MM" timestamp from the most recent ingest, and a stale-data warning if older than ~30 minutes during market hours. Effort: ~1 hour.
P1 — Beta quality
6. No disclaimer on the page

Even for a free, ungated beta: one visible line — "Educational and informational only. Not investment advice." Cheap insurance, and it sets user expectations correctly from day one.

P1 — Beta quality
7. No feedback capture — beta's entire job is learning

Without a thumbs up/down or a "did you act on this?" control per signal, two weeks of beta will produce signals but zero evidence anyone found them useful. Learning is the only reason to run a beta.

P1 — Beta quality
8. Nobody knows the tab exists, and MACD is jargon

No announcement to the 8 existing accounts. No onboarding tooltip explaining what a MACD crossover means to a non-technical NRI investor. A tab nobody visits generates no beta learning.

P2 — Next phase, highest priority
9. Auth gate + tiering + Telegram fan-out ("the full loop")
"Step by step" vs. "the full loop" — explained simply

Option A — Steps. Ship the login gate first (~1 day). Users can log in and see the tab. Telegram alerts come weeks later.

Option B — Full loop. Build everything at once (~1 week): login gate + a "Connect Telegram" button + the sending engine + alert preferences. Nothing goes live until the whole chain works end to end.

Recommended — Option C. Do neither yet. Leave the beta open, get the bot actually producing signals, watch the data for a week or two. Then build the full loop in one go — because by then we will know what the alert should actually say, which is unknown today.

What the full loop requires, in order:

  1. Identity restored — re-enable the sign-in gate (the code is in git history on lib/db/schema/auth.ts, app/api/analysis/momentum-signals/route.ts, app/momentum-radar/page.tsx). No login means no way to send anyone a personal alert.
  2. Telegram linking — user clicks "Connect Telegram" in Fortress, receives a one-time code, sends it to the new Fortress Alerts bot, and we store their telegram_chat_id against their account.
  3. Fan-out sender lives in Fortress, not in the trading bot. When a new signal lands, Fortress pushes it to every linked, entitled user. The trading bot's job is trading — a Telegram outage must never be able to stall an order.
  4. User preferences — Daily only vs Daily+Weekly, sector filter, max alerts per day. Without this, a 500-stock scan will spam people into muting the channel within a week.
Owner decision: parked as the highest-priority next phase, to begin after 1–2 weeks of beta testing.

6. Important: the web tab does not need Telegram at all

These are two independent consumers of the same data

The web tab reads the macd_signals table directly from the database. Telegram would be a separate downstream consumer of that same table — and it does not exist yet.

Therefore: the beta needs nothing whatsoever from Telegram. Signals will be fully visible on the UI with zero Telegram IDs, zero linking, and zero sending engine. Telegram is purely additive, later.

8. Known gotchas for the next session

  • CI/CD may finish the VPS build but silently skip pm2 restart. Observed once in Session 30c with no visible error. The workflow needs an explicit "restart confirmed" check that fails loudly rather than trailing off silently. Until then, verify .next/BUILD_ID changed and the process actually restarted after every deploy.
  • Duplicate CRON_SECRET entries were found in the VPS .env.production (two different values). Cleaned up in Session 30b — but always confirm the live value with pm2 env before debugging any 401 on the ingest endpoint.
  • The bot's GitHub repo belongs to a different account with no push access. Bot code was copied to /opt/macd-bot over SSH, not via git. Any bot code change must be copied the same way.
  • Credentials can be changed from the browser via /momentum-radar/admin → POST /api/admin/bot-config, which writes directly into /opt/macd-bot/.env and restarts the bot. No SSH needed for key rotation.
