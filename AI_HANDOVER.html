VPS Operations — PM2 Process Management

ACTIVE Three PM2 Processes Running on VPS

All processes are auto-managed by PM2. Check status, logs, and restart via standard commands.

Process Type Purpose Port/IO
fortress-app Node.js Next.js app (web UI, API routes) Port 3000
fortress-cron Node.js Scanner cron jobs (NSE/US scans every 5 min) Logs only
fortress-bot Python 3 MACD bot (scans Nifty 500 every 5 min, posts to Momentum Radar) Logs only
REFERENCE Common PM2 Commands (VPS)
  • pm2 status — Show all processes (status, PID, memory, uptime)
  • pm2 logs fortress-bot — Watch bot logs in real-time
  • pm2 logs fortress-bot --lines 50 — Show last 50 lines
  • pm2 restart fortress-bot --update-env — Restart bot with fresh env vars
  • pm2 restart all --update-env — Restart all three processes
  • pm2 stop fortress-bot — Stop bot (temporary)
  • pm2 start fortress-bot — Start bot again
  • pm2 save && pm2 startup — Save config and enable auto-start on server reboot
DEPLOYMENT FLOW Deploy New Code (Standard Process)
  • Push commits to main branch
  • GitHub Actions CI runs build + test
  • On success, trigger VPS deploy: git pull && npm run build && pm2 restart all --update-env
  • All three PM2 processes restart automatically with fresh code + env vars
  • No manual steps required (PM2 handles process lifecycle)
IMPORTANT Bot Environment Variables (Must Be Set in .env.production)

These are required for the bot to function. Without them, the bot crashes on startup.

  • TELEGRAM_BOT_TOKEN — Bot token from Telegram BotFather
  • TELEGRAM_ADMIN_ID — Your Telegram chat ID (for alerts)
  • FORTRESS_API_URL — https://fortressintelligence.space/api/analysis/momentum-signals
  • FORTRESS_CRON_SECRET — Shared secret (same value as CRON_SECRET)
  • ZERODHA_API_KEY, ZERODHA_API_SECRET, ZERODHA_CLIENT_ID — Optional (for auto-trading)

⚠️ NOTE: If these are missing, the bot will crash and PM2 will keep restarting it. Check pm2 logs fortress-bot for errors.

Most Recent Session — Auth Breakage & Momentum Radar Gate Removed

KNOWN ISSUE Password reset is broken in production.

Root cause: SMTP is not configured on the VPS (SMTP_HOST/SMTP_USER/SMTP_PASSWORD). /api/auth/forgot-password deliberately swallows the email-send failure and always returns success (this is correct behavior — it avoids leaking which emails are registered) — but it means no reset email ever actually arrives, with no visible error anywhere. This has been a known backlog item since Session 28 and was never completed.

This surfaced because a user (arundsamant@gmail.com) couldn't reset their password. That exact email does not appear to match any row in auth_user — needs a manual DB check (see Backlog).

WORKAROUND SHIPPED POST /api/admin/generate-reset-link

Admin-only endpoint (shared x-cron-secret auth, same pattern as the scan crons) that mints a valid PASSWORD_RESET token directly and returns the reset URL — bypassing email entirely. Use it to manually unblock a user until SMTP is fixed: 

curl -X POST https://fortressintelligence.space/api/admin/generate-reset-link \
  -H "Content-Type: application/json" \
  -H "x-cron-secret: <CRON_SECRET from /opt/fortress/.env.production>" \
  -d '{"email":"user@example.com"}'

Commit: ad2b3b6b. Retire this once SMTP is fixed and forgot-password is verified end-to-end.
