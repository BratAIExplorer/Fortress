✅ CRITICAL FIX DEPLOYED 🔧 Three Major Regressions Restored — Bot Logic Now 100% Identical to Standalone

ISSUE: Fortress bot found 0 MACD crossovers while standalone bot found 57 on identical data (2026-07-29). Root cause: 3 critical logic regressions introduced during migration.

The Three Regressions (ALL FIXED)

Regression Before (Broken) After (Fixed) Lines
Recency Filter 0–1 days old only ✅ 0–3 days old (exact standalone) 174–200
EMA Calculations 3 EMAs only (20, 50, 200) ✅ All 6 EMAs (9, 20, 50, 100, 150, 200) 163–168
Target/SL Selection Hardcoded rules (always EMA20→target1, EMA50→target2, EMA200→SL) ✅ Dynamic EMA selection (nearest/highest above CMP = target, below CMP = SL) 214–265

Detailed Fix Breakdown

  • Regression #1 — Recency Filter (Lines 174–200):

    Fortress was checking only today and yesterday for crossovers. Standalone checks up to 3 days back (capturing crossovers that occurred Mon/Tue even if scanning Wed). This filter change alone rejected 25+ valid signals.

    • Before: if not (crossover_today or crossover_yesterday): return None
    • After: if crossover_today: ... elif crossover_yesterday: ... elif crossover_2_days: ... elif crossover_3_days: ...
  • Regression #2 — EMA Calculations (Lines 163–168):

    Fortress was calculating only 3 EMAs. Standalone calculates all 6. This limited target/SL selection to only EMA20/50/200, missing intermediate levels (100, 150) that signals may use.

    • Before: ema20, ema50, ema200 only
    • After: ema9, ema20, ema50, ema100, ema150, ema200
  • Regression #3 — Target/SL Selection (Lines 214–265):

    Fortress was using hardcoded rules. Standalone uses dynamic selection: iterate all available EMAs, find nearest EMA above CMP (first target), find highest EMA above CMP (final target), find nearest EMA below CMP (stop loss). This ensures targets/SL match the actual market structure.

    • Before: target1 = EMA20 if EMA20 > CMP else 5% default (always tries EMA20)
    • After: targets = {EMA20, EMA50, EMA100, EMA150, EMA200 | EMA > CMP} → target1 = min(targets) → target_final = max(targets) (picks nearest, then highest)

🟡 PHASE 2 — after 1–2 weeks of beta

Priority Item Detail & implication
P0 Separate the trading bot from the user-alerts bot Owner decision 29 Jul: do this within one week, before any user-facing Telegram work begins.

Explained simply: a Telegram bot is like a phone number. Today there is one number, and the trading bot uses it to text the owner "I just bought 50 SBIN." If that same number is later given to 500 customers: (1) everyone's messages come through the same phone and wires get crossed; (2) Telegram caps messages per second, so a customer blast could delay the owner's own trade alert — the one message that must arrive instantly; (3) if a customer reports or blocks the number and Telegram restricts it, the owner's trading alerts die too; (4) customer messaging can never change without touching the live trading setup.

So: get a second phone number. One bot for the owner's trading, a separate "Fortress Alerts" bot for customers. Free, 2 minutes today. Untangling it after 500 people are on it takes a weekend.
P0 Signal language — observation vs. recommendation "MACD crossover detected on SBIN" is an observation — it describes what the market did. "Buy SBIN, target ₹X, stop loss ₹Y" is a recommendation — it tells a person what to do with their money. A free read-only web table sits closer to the first; a paid push notification to a stranger's phone sits much closer to the second, which is SEBI Research Analyst / Investment Adviser territory in India. It is the paywall plus the push that changes the risk profile, not the wording alone.

Owner decision 29 Jul: continue beta as-is. This is a hard blocker before the first rupee is charged. Requires proper Indian regulatory review — not a judgement call made in a build session.
